# GraphDB OWL Inferencing Guide

This document explains how CIDOC-CRM OWL inferencing works in GraphDB and provides query patterns for leveraging inferred knowledge.

## Overview

GraphDB's OWL-Horst (Optimized) reasoning automatically generates **inferred triples** based on the CIDOC-CRM ontology. These inferences include:

1. **Inverse properties** (P108 ↔ P108i, P14 ↔ P14i, etc.)
2. **Class hierarchies** (E12_Production is also E2_Temporal_Entity)
3. **Property hierarchies** (rdfs:label is also P1_is_identified_by)

## How Inferencing Works in GraphDB

### Named Graphs vs. Default Graph

GraphDB separates **asserted** and **inferred** triples:

- **Asserted triples**: Your actual data, stored in named graphs like `<http://aa.perseus.org/graph/linkedart/HAM>`
- **Inferred triples**: Generated by the reasoner, stored in the **default inference context**

When you query:
- **WITH GRAPH clause**: You see only asserted triples in that specific graph
- **WITHOUT GRAPH clause**: GraphDB automatically merges all graphs including inferences

### Example: Inverse Properties

In your data (asserted):
```turtle
<production123> crm:P108_has_produced <object456> .
```

GraphDB infers (based on OWL inverse property axiom):
```turtle
<object456> crm:P108i_was_produced_by <production123> .
```

**Query WITH GRAPH (sees only asserted):**
```sparql
SELECT * WHERE {
  GRAPH <http://aa.perseus.org/graph/linkedart/HAM> {
    ?obj crm:P108i_was_produced_by ?prod .
  }
}
# Returns: 0 results (inverse not in named graph)
```

**Query WITHOUT GRAPH (sees asserted + inferred):**
```sparql
SELECT * WHERE {
  ?obj crm:P108i_was_produced_by ?prod .
}
# Returns: 8,806 results (inference works!)
```

## Confirmed Inferences in Our Data

### 1. Class Hierarchy Reasoning

GraphDB infers that instances of a class are also instances of all superclasses.

**Example: E12_Production → E2_Temporal_Entity**

| Query | Count |
|-------|-------|
| `?x a crm:E12_Production` | 8,806 |
| `?x a crm:E2_Temporal_Entity` | 17,724 |

The larger count for E2_Temporal_Entity includes:
- All E12_Production instances (8,806)
- E67_Birth instances
- E69_Death instances
- Other temporal entity types

**Query:**
```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>

SELECT ?type (COUNT(?event) AS ?count) WHERE {
  ?event a crm:E2_Temporal_Entity ;
         a ?type .
}
GROUP BY ?type
ORDER BY DESC(?count)
```

### 2. Inverse Property Reasoning

GraphDB automatically generates inverse properties for all CIDOC-CRM bidirectional properties.

**Example: P108_has_produced ↔ P108i_was_produced_by**

Both directions return the same data (8,806 triples):

```sparql
# Forward property (asserted in data)
SELECT (COUNT(*) AS ?count) WHERE {
  ?prod crm:P108_has_produced ?obj .
}
# Returns: 8,806
```

```sparql
# Inverse property (inferred by GraphDB)
SELECT (COUNT(*) AS ?count) WHERE {
  ?obj crm:P108i_was_produced_by ?prod .
}
# Returns: 8,806
```

**Example: P14_carried_out_by ↔ P14i_performed**

Both directions return the same data (2,011 triples):

```sparql
# Forward property (asserted in data)
SELECT (COUNT(*) AS ?count) WHERE {
  ?prod crm:P14_carried_out_by ?person .
}
# Returns: 2,011
```

```sparql
# Inverse property (inferred by GraphDB)
SELECT (COUNT(*) AS ?count) WHERE {
  ?person crm:P14i_performed ?prod .
}
# Returns: 2,011
```

### 3. Property Hierarchy Reasoning

The CIDOC-CRM Supplement declares `rdfs:label` as a subproperty of `P1_is_identified_by`.

**Example: rdfs:label → P1_is_identified_by**

| Query | Count |
|-------|-------|
| `?obj rdfs:label ?label` | 8,806 |
| `?obj crm:P1_is_identified_by ?id` | 301,191 |

The P1 count includes:
- All rdfs:label values (8,806 inferred)
- All explicit identifier nodes (title nodes, accession numbers, etc.)

**Query to see inference:**
```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?identifier ?identifierType WHERE {
  ?obj a crm:E22_Human-Made_Object ;
       rdfs:label "Tetradrachm of Alexander III the Great, Macedonia?"@en .

  # P1_is_identified_by includes the rdfs:label via inference
  ?obj crm:P1_is_identified_by ?identifier .

  OPTIONAL {
    BIND(datatype(?identifier) AS ?identifierType)
    FILTER(isLiteral(?identifier))
  }
}
```

Result includes the literal string as one of the P1_is_identified_by values!

## Query Patterns

### Pattern 1: Simple Inverse Property

Use inverse properties to query in the natural direction for your question.

```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

# Find objects and what produced them (using inverse)
SELECT ?objLabel ?prodLabel WHERE {
  ?obj a crm:E22_Human-Made_Object ;
       rdfs:label ?objLabel ;
       crm:P108i_was_produced_by ?prod .

  ?prod rdfs:label ?prodLabel .
}
LIMIT 10
```

### Pattern 2: Property Chain Reasoning

Combine inverse properties with asserted properties to traverse relationships.

```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

# Find objects and their creators using property chains
# object → P108i_was_produced_by → production → P14_carried_out_by → person
SELECT ?objLabel ?prodLabel ?personLabel ?role WHERE {
  ?obj a crm:E22_Human-Made_Object ;
       rdfs:label ?objLabel ;
       crm:P108i_was_produced_by ?prod .

  ?prod rdfs:label ?prodLabel ;
        crm:P14_carried_out_by ?person .

  ?person rdfs:label ?personLabel .

  # Get role from property class if available
  OPTIONAL {
    ?roleAssignment crm:P01_has_domain ?prod ;
                    crm:P02_has_range ?person ;
                    crm:P14.1_in_the_role_of ?roleType .
    ?roleType rdfs:label ?role .
  }
}
LIMIT 10
```

### Pattern 3: Class Hierarchy Queries

Query for superclasses to find all instances of related types.

```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>

# Find all temporal entities (includes E12_Production, E67_Birth, E69_Death, etc.)
SELECT ?type (COUNT(?event) AS ?count) WHERE {
  ?event a crm:E2_Temporal_Entity ;
         a ?type .
}
GROUP BY ?type
ORDER BY DESC(?count)
```

### Pattern 4: Mixed GRAPH and Inference

Use GRAPH only where you need to restrict specific patterns; let other patterns use inference.

```sparql
PREFIX crm: <http://www.cidoc-crm.org/cidoc-crm/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?objLabel ?prod WHERE {
  # Use inferred inverse property (from default graph)
  ?obj crm:P108i_was_produced_by ?prod .

  # But still filter to data from specific graph
  GRAPH <http://aa.perseus.org/graph/linkedart/HAM> {
    ?obj a crm:E22_Human-Made_Object ;
         rdfs:label ?objLabel .
  }
}
LIMIT 10
```

## Best Practices

### ✅ DO

1. **Query without GRAPH clause** when you want inferencing to work
   ```sparql
   SELECT * WHERE {
     ?obj crm:P108i_was_produced_by ?prod .
   }
   ```

2. **Use inverse properties naturally** - don't work around them
   ```sparql
   # Good: Natural direction
   ?object crm:P108i_was_produced_by ?production .

   # Avoid: Awkward direction
   ?production crm:P108_has_produced ?object .
   FILTER(?object = <specific-object>)
   ```

3. **Query superclasses** for broader results
   ```sparql
   # Finds all temporal entities, not just productions
   ?event a crm:E2_Temporal_Entity .
   ```

4. **Use FROM** if you need to specify graphs explicitly
   ```sparql
   SELECT *
   FROM <http://aa.perseus.org/graph/linkedart/HAM>
   WHERE {
     ?obj crm:P108i_was_produced_by ?prod .
   }
   ```

### ❌ DON'T

1. **Don't use GRAPH clause** if you need inferred properties
   ```sparql
   # This won't see inverse properties
   GRAPH <http://aa.perseus.org/graph/linkedart/HAM> {
     ?obj crm:P108i_was_produced_by ?prod .
   }
   ```

2. **Don't use wrong property directions**
   ```sparql
   # Wrong: Production doesn't "perform" - person performs!
   ?prod crm:P14i_performed ?person .

   # Right: Production is "carried out by" person
   ?prod crm:P14_carried_out_by ?person .
   ```

3. **Don't filter on labels without checking they exist**
   ```sparql
   # This fails if labels are missing
   ?prod rdfs:label ?prodLabel .

   # Better: Make label optional
   OPTIONAL { ?prod rdfs:label ?prodLabel }
   ```

## Common Property Pairs

| Forward Property | Inverse Property | Usage |
|-----------------|------------------|-------|
| `P108_has_produced` | `P108i_was_produced_by` | Production → Object / Object → Production |
| `P14_carried_out_by` | `P14i_performed` | Activity → Actor / Actor → Activity |
| `P1_is_identified_by` | `P1i_identifies` | Entity → Identifier / Identifier → Entity |
| `P2_has_type` | `P2i_is_type_of` | Entity → Type / Type → Entity |
| `P92i_was_brought_into_existence_by` | `P92_brought_into_existence` | Entity → Birth / Birth → Entity |
| `P93i_was_taken_out_of_existence_by` | `P93_took_out_of_existence` | Entity → Death / Death → Entity |

## Troubleshooting

### Problem: Inverse property returns 0 results

**Symptom:**
```sparql
GRAPH <http://aa.perseus.org/graph/linkedart/HAM> {
  ?obj crm:P108i_was_produced_by ?prod .
}
# Returns: 0 results
```

**Solution:** Remove the GRAPH clause
```sparql
?obj crm:P108i_was_produced_by ?prod .
# Returns: 8,806 results
```

### Problem: Query with labels returns 0 results

**Symptom:**
```sparql
?prod crm:P14i_performed ?person .
?prod rdfs:label ?prodLabel .
?person rdfs:label ?personLabel .
# Returns: 0 results
```

**Solutions:**
1. Check property direction (use `P14_carried_out_by` from production to person)
2. Make labels optional if they might be missing
3. Verify the entities actually have labels with a simpler query first

### Problem: Not seeing class hierarchy

**Symptom:**
```sparql
?event a crm:E2_Temporal_Entity .
# Returns same count as E12_Production
```

**Solution:** Verify OWL-Horst reasoning is enabled in GraphDB:
1. Go to Setup → Repositories
2. Select your repository
3. Check "Ruleset" is set to "OWL-Horst (Optimized)" or "OWL-Max"
4. Restart repository if needed

## Performance Considerations

- **Inferencing adds overhead**: 2.8M total triples vs. 1.3M asserted (2x increase)
- **Queries without GRAPH are slower**: GraphDB must check all graphs and inferences
- **Use OPTIONAL carefully**: Complex OPTIONAL patterns can be expensive
- **Limit results early**: Use LIMIT when testing queries
